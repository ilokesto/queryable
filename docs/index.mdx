# Queryable

Version **0.0.1**, private beta. Unpublished on npm; the local documentation site covers the `next` channel only.

```ts
import { createQueryable, WHERE, SORT, LIMIT, MAP, VALUES } from "@ilokesto/queryable";

const users = createQueryable({
  alice: { name: "Alice", age: 25 },
  bob: { name: "Bob", age: 30 },
  charlie: { name: "Charlie", age: 20 },
});

const names = users
  [WHERE](user => user.age >= 25)
  [SORT]((a, b) => b.age - a.age)
  [LIMIT](2)
  [MAP](user => user.name)
  [VALUES](); // ["Bob", "Alice"]
```

## Operations

| Operation | Result |
| --- | --- |
| `[WHERE]((value, key) => boolean)` | Matching records; type guards narrow the value type |
| `[SORT]((a, b) => number)` | Stable ordered `QuerySequence`, including numeric keys |
| `[MAP]((value, key) => next)` | Transformed values with original record keys |
| `[PICK](...keys)` | Whole values for existing **record keys**; missing/duplicate keys ignored |
| `[LIMIT](n)` | Entries selected by `slice(0, n)` |
| `[GROUP_BY]((value, key) => K)` | Materialized groups; `Partial<Record<K, ...>>` preserves literal keys |
| `[COUNT]()` | Number of records |
| `[FIRST]()` | First value or `undefined` |
| `[VALUES]()` | Fresh value array |
| `[FIND]((value, key) => boolean)` | First matching value, with type guard narrowing, or `undefined` |
| `[SOME]((value, key) => boolean)` | Boolean; stops on the first match |
| `[ENTRIES]()` | Fresh `[key, value]` tuples in query order |
| `[TO_OBJECT]()` | Ordinary shallow object, without query methods |
| `[REDUCE]((acc, value, key) => next, initial)` | Fold in query order; initial is required |
| `[LAZY]()` | Repeatable, non-memoized deferred sequence |

## Records, ordering, and migration

`createQueryable` returns a mutable `Queryable<T>` record. Its eager `WHERE`, `MAP`, `PICK`, and `LIMIT` return new records. `SORT` returns `QuerySequence<T>`: ordered entries rather than a record whose numeric keys could reorder themselves. Subsequent transformations keep the sequence representation. Use `VALUES` or `ENTRIES` to preserve order; `TO_OBJECT` intentionally restores native object key ordering. Do not use record indexing, object spread, or JSON on sequences to extract their data.

```ts
import { createQueryable, SORT, LIMIT, ENTRIES, TO_OBJECT } from "@ilokesto/queryable";

const sorted = createQueryable({ 1: 10, 2: 20 })[SORT]((a, b) => b - a);
sorted[LIMIT](1)[ENTRIES](); // [["2", 20]]
sorted[TO_OBJECT](); // ordinary object; numeric keys enumerate as "1", "2"
```

This private beta intentionally removes `SELECT`: rename imports and calls to `PICK`. It still selects **record keys**, not fields inside values. Use `MAP(user => ({ name: user.name }))` for field projection. Record `PICK` uses argument insertion order subject to native numeric-key ordering; sequence `PICK` preserves argument order exactly.

## Lazy evaluation and short-circuiting

```ts
import { createQueryable, LAZY, WHERE, MAP, LIMIT, VALUES } from "@ilokesto/queryable";

const query = createQueryable({ a: 1, b: 2, c: 3, d: 4 });
const firstEven = query[LAZY]()
  [WHERE](n => n % 2 === 0)
  [MAP](n => n * 10)
  [LIMIT](1);
firstEven[VALUES](); // [20]; only a and b reach the predicate
```

- Eager queries run callbacks when an operation is called. `LAZY` defers subsequent `WHERE`, `MAP`, `PICK`, `LIMIT`, and `SORT` until a terminal call.
- `VALUES`, `ENTRIES`, `TO_OBJECT`, `COUNT`, `REDUCE`, `FIRST`, `FIND`, `SOME`, and `GROUP_BY` consume pending work. `FIRST`, `FIND`, `SOME`, and nonnegative `LIMIT` can stop upstream iteration early; `LIMIT(0)` never consumes the source.
- `SORT`, sequence `PICK`, and finite negative `LIMIT` need the full upstream input. They buffer on consumption. `GROUP_BY` always executes immediately and returns eager snapshot groups: records for record queries, sequences for sequence queries.
- Each consumption starts fresh and reruns deferred callbacks. There is no cache. Errors propagate at consumption, and another consumption starts a fresh attempt.
- A record's lazy view reads that **query record** at consumption, so mutations between consumptions are visible. Changes to the original input object are not: construction already shallow-copied it. An eager sorted sequence is a snapshot; adding `LAZY` afterward does not rerun its already executed sort.
- Values are shallow references, not deeply frozen. Callbacks should not add, delete, or replace source records during a traversal; mutation during traversal is not a snapshot-isolation contract.

For a single lookup, prefer `query[FIND](predicate)` or `query[SOME](predicate)`. `query[WHERE](predicate)[FIRST]()` still eagerly builds the entire filtered record.

## Types and aggregation

```ts
import { createQueryable, WHERE, GROUP_BY, REDUCE } from "@ilokesto/queryable";

const mixed = createQueryable<number | string>({ a: 1, b: "two" });
const strings = mixed[WHERE]((value): value is string => typeof value === "string");
// Queryable<string>
const groups = createQueryable({ a: 1, b: 2, c: 3 })
  [GROUP_BY](n => n % 2 ? "odd" : "even");
const oddTotal = groups.odd?.[REDUCE]((sum, n) => sum + n, 0); // 4
// A possible group key may be absent, including for empty input.
```

## Contract and limitations

- Own enumerable string keys are data. Inherited, non-enumerable, and Symbol-keyed input properties are not copied. `__proto__`, `constructor`, and `toString` are supported as ordinary data keys; the shared prototype has a null root.
- Construction and query operations make shallow copies. Values remain shared references. Queries are mutable records, but operations do not mutate their source.
- `LIMIT` retains native `slice` semantics: negative numbers drop trailing entries, fractions truncate, `NaN` gives an empty result, and `Infinity` keeps all entries.
- Methods need their receiver: call `query[WHERE](predicate)`, not a detached method. Object spread and JSON on records retain data but lose query methods.
- Methods are shared and frozen, not bound per instance. This is a structural allocation choice, not a promise of a particular heap reduction or runtime speed.

## Predicate narrowing and property groups

`WHERE(Boolean)` and `FIND(Boolean)` remove literal `false`, `0`, `0n`, `""`, `null`, and `undefined` from the value type. Broad `number`, `bigint`, and `string` stay broad: TypeScript cannot express all nonzero, non-NaN numbers or nonempty strings. A callback returning literal `false` gives an empty `Queryable<never>` or `QuerySequence<never>`; `FIND` returns `undefined`. Explicit and inferred type guards still narrow, while ordinary boolean callbacks keep the original value type. These signatures apply to eager records, ordered sequences, and lazy sequences without changing evaluation order.

```ts
import { createQueryable, WHERE, FIND, VALUES, isDefined, isNonNullish, negate } from "@ilokesto/queryable";

const mixed = createQueryable<0 | false | "" | "cat" | null | undefined>({
  zero: 0, no: false, empty: "", cat: "cat", nil: null, missing: undefined,
});
mixed[WHERE](Boolean)[VALUES](); // ["cat"]; Queryable<"cat">
mixed[WHERE](isDefined)[VALUES](); // [0, false, "", "cat", null]
mixed[WHERE](isNonNullish)[VALUES](); // [0, false, "", "cat"]
mixed[WHERE](negate(isNonNullish))[VALUES](); // [null, undefined]
mixed[FIND](() => false); // undefined
```

`isDefined` excludes only `undefined`; `isNonNullish` excludes `null` and `undefined`. `negate(predicate)` forwards all callback arguments and negates its result. Only the supplied, branded `isDefined` and `isNonNullish` helpers have complement narrowing. Arbitrary guards return a boolean predicate: a guard for positive numbers may also reject negative numbers, so its negation cannot safely exclude all numbers. Wrapping either helper in an ordinary callback loses the branded complement contract.

`GROUP_BY_PROP(property)` correlates string discriminant keys with the union members that can have that property value. Unlike callback-based `GROUP_BY`, its groups narrow independently and remain optional, even for required discriminants or empty input.

```ts
import { createQueryable, GROUP_BY_PROP, VALUES } from "@ilokesto/queryable";

type Pet = { readonly kind: "cat"; meow: true } | { readonly kind: "dog"; bark: true };
const pets = createQueryable<Pet>({ alice: { kind: "cat", meow: true } });
const groups = pets[GROUP_BY_PROP]("kind");
groups.cat?.[VALUES](); // cat members only, with original key "alice"
groups.dog; // undefined here; Queryable<dog member> | undefined
```

Optional string discriminants and union members without the property are supported. Missing or `undefined` values are skipped, not coerced to a group name. Group member types preserve their original optional and readonly properties conservatively; grouping does not rewrite an optional property as required. Numeric or mixed string/number discriminant properties are not accepted; there is no implicit numeric-key coercion guarantee. At runtime, only string property values form groups.

Like `GROUP_BY`, `GROUP_BY_PROP` consumes its input immediately, including pending lazy work, and returns eager shallow snapshots. It reads each member's discriminant once in traversal order, preserves original member keys and record/sequence mode, supports empty and special string keys, and never repeats grouping work when a group is consumed again. Property getter errors propagate unchanged. Nested values remain shared references.

## Selector ordering and explicit selection

```ts
import {
  createQueryable, SORT_BY, MIN_BY, MAX_BY, TOP_K, NTH_BY, RANK_BY, ENTRIES,
} from "@ilokesto/queryable";

const scores = createQueryable({
  alice: { team: "a", score: 8 },
  bob: { team: "a", score: 9 },
  charlie: { team: "b", score: 9 },
});
scores[SORT_BY](
  { select: user => user.team },
  { select: user => user.score, direction: "desc" },
)[ENTRIES](); // bob, alice, charlie
scores[MIN_BY]({ select: user => user.score }); // alice's value
scores[MAX_BY]({ select: user => user.score }); // bob's value (first tie)
scores[TOP_K](2, { select: user => user.score, direction: "desc" })[ENTRIES]();
// [["bob", ...], ["charlie", ...]]
scores[NTH_BY](-1, { select: user => user.score }); // charlie's value
scores[RANK_BY]("charlie", { select: user => user.score }); // 2
```

Every operation requires one or more `OrderRule<T>` objects with a `select(value, key)` callback and optional `direction: "asc" | "desc"` (default `"asc"`). Rules compare lexicographically. `OrderKey` is `boolean | number | bigint | string | null | undefined`. Ascending category order is **boolean, number, bigint, string, null, undefined**, with no coercion across categories. Within categories, `false < true`, numbers and bigints use numeric order, and strings use JavaScript UTF-16 lexical order (not locale collation). `NaN` follows all other numbers, including `Infinity`; all NaNs tie. `-0` and `0` tie. Descending reverses the whole key order, including nullish placement. Equal complete rule keys retain input order in either direction.

`SORT_BY` and `TOP_K` return ordered `QuerySequence<T>` results, retaining original keys, including integer and special keys. `SORT_BY` computes every rule once per entry, even when an earlier rule already distinguishes entries. Cached keys exist only during that consumption, never across lazy consumptions. Eager calls run immediately; lazy chains defer until consumed, rescan their live query record, and rerun selectors. Eager results retain a shallow snapshot of entries. Source records and entry arrays are never sorted in place; nested values remain shared references. Exceptions propagate unchanged, at the same eager/deferred boundary as `SORT`. Existing comparator `SORT`, repeated `SORT`, and `SORT` + `LIMIT`/`FIRST` are not rewritten.

`MIN_BY` and `MAX_BY` are immediate terminals, even on lazy chains. They scan once, retain only the best entry and its rule keys, and replace it only for a strict improvement. They return **values**, not entries; a first tied value wins for both extrema. Empty input returns `undefined`, which is indistinguishable from a selected undefined value; use `RANK_BY` to test an existing key's position or `TOP_K(...)[ENTRIES]()` when key/presence information matters. Directions apply to extrema too: a descending rule's minimum has the greatest natural key.

`TOP_K(k, ...rules)` retains at most K candidates in a bounded heap, then stably sorts the winners; it is ordered even when K exceeds the input length. K must be a nonnegative safe integer; `NaN`, infinities, fractions, negative values, and unsafe integers throw `RangeError` at the operation call, before consuming even a lazy source. `-0` means zero. K=0 does not read upstream or call selectors. Positive K consumes the full upstream input before yielding winners, even if followed by `FIRST` or `LIMIT`.

`NTH_BY(index, ...rules)` returns the value at a **zero-based stable ordinal** in the same ordering. Negative indexes count from the end (`-1` is last); empty or out-of-range positions return `undefined`. Indexes must be safe integers; invalid indexes throw `RangeError` before consuming. `RANK_BY(recordKey, ...rules)` returns that key's zero-based stable ordinal, or `undefined` if absent. Ties receive distinct consecutive positions according to input order, not competition/dense ranks. Both are immediate terminals and cache each selector once per entry per call.

For N entries and R rules, `SORT_BY` uses O(NR) cached-key storage plus sorting; extrema use O(R) working storage. `TOP_K` uses O(min(K,N)R) retained keys and O(N log(min(K,N)) + min(K,N) log(min(K,N))) comparison work. `NTH_BY` uses an iterative heap of at most `index + 1` candidates for nonnegative indexes or `abs(index)` candidates for negative indexes; no recursive partitioning occurs. `RANK_BY` buffers O(NR) keys, locates the requested key, and counts preceding candidates without sorting. These are explicit selection operations, not automatic optimizations. See [ordering measurements](../bench/ORDERING.md) for K/N and selector-cost trade-offs; no speedup or heap threshold is promised.

## Partition, running accumulators, and effects

`PARTITION(predicate)` immediately consumes the query once and returns
`[matching, nonmatching]`, two independent eager shallow snapshots even for a lazy
source. The predicate receives `(value, originalKey)` exactly once per entry in
query order. Records retain native object ordering; sequences retain their input
order. Type guards narrow only the matching side; the nonmatching side keeps `T`
because a guard may recognize only some values of its claimed type. Empty sides
remain typed queries. Later source assignments do not alter either snapshot, but
referenced values are still shared.

```ts
import {
  createQueryable, PARTITION, SCAN, TAP, EACH, THROUGH, LAZY, LIMIT, VALUES,
} from "@ilokesto/queryable";

const mixed = createQueryable<string | number>({ a: "one", b: 2 });
const [strings, rest] = mixed[PARTITION](value => typeof value === "string");
// Queryable<string>, Queryable<string | number>

const totals = createQueryable({ a: 1, b: 2, c: 3 })[LAZY]()
  [SCAN]((sum, value, key) => sum + value, () => 0)
  [TAP]((value, key) => { console.info(key, value); });
totals[LIMIT](2)[VALUES](); // [1, 3]; effects only for a and b
totals[EACH]((value, key) => { console.info(key, value); }); // all entries, again
const firstTwo = totals[THROUGH](query => query[LIMIT](2)[VALUES]()); // number[]
```

`SCAN(reducer, seedFactory)` emits one accumulator at every original input key,
preserving record/sequence mode. It does not emit an extra seed entry. The reducer
receives `(accumulator, value, originalKey)`. The required zero-argument factory
runs once at the start of each consumption, including empty consumption; an
unconsumed lazy chain or downstream `LIMIT(0)` does not call it. Return a fresh
mutable seed from the factory to keep lazy consumptions independent.

Accumulators are **not cloned**: if the reducer mutates and returns the same
object, earlier emitted values alias that object and observe its later mutations.
Return a new object at each step when independent historical values are needed.
Empty input emits nothing and does not call the reducer.

`TAP(effect)` retains every original key and value identity. Like `SCAN`, it runs
immediately on eager queries and on demand in lazy queries; each lazy consumption
repeats the work against the live source without memoization. `LIMIT`, `FIND`,
`FIRST`, and `SOME` can stop downstream demand early. `EACH(effect)` is a terminal:
it visits entries in order, returns `void`, and does not collect a result array.
Both effects receive `(value, originalKey)`; returning `false` does not stop them.
Empty queries call neither effect.

`THROUGH(fn)` immediately calls `fn` once with the exact query object, without
consuming it, and preserves the function's return type and result identity.
All five methods require their receiver, use shared frozen prototypes, and
propagate callback exceptions without wrapping or changing the thrown value.

## Value distinctness

| Operation | Result |
| --- | --- |
| `[DISTINCT]()` | First entry for every distinct value across the whole input |
| `[DISTINCT_BY]((value, key) => selected)` | First entry for every distinct selected value |
| `[DISTINCT_UNTIL_CHANGED]()` | First entry of each adjacent run of equal values |
| `[DISTINCT_UNTIL_CHANGED_BY]((value, key) => selected)` | First entry of each adjacent run of equal selected values |

```ts
import {
  createQueryable, DISTINCT, DISTINCT_BY, DISTINCT_UNTIL_CHANGED, ENTRIES,
} from "@ilokesto/queryable";

const numbers = createQueryable({ a: 1, b: 1, c: 2, d: 1 });
numbers[DISTINCT]()[ENTRIES](); // [["a", 1], ["c", 2]]
numbers[DISTINCT_UNTIL_CHANGED]()[ENTRIES](); // [["a", 1], ["c", 2], ["d", 1]]
const users = createQueryable({
  alice: { department: "design" },
  bob: { department: "design" },
  charlie: { department: "engineering" },
});
users[DISTINCT_BY](user => user.department)[ENTRIES]();
// Keeps alice and charlie, with their original values and keys.
```

Equality is **SameValueZero**: `NaN` equals `NaN`, and `-0` equals `0`.
`undefined` is an ordinary value, including at the start of an adjacent run.
Objects and functions compare by reference identity, never by inspecting their
contents. Selectors receive the original value and key once per visited entry;
the selected value is used only for equality, not as a replacement value or key.
There is no custom comparator API. Arbitrary equality can require comparing each
candidate with prior representatives rather than using Set membership.

Record keys are already unique; that does not make their **values** unique.
`PICK` ignores repeated requested keys, whereas distinct operations compare values
or selector results across different original keys. The first matching entry wins.
Records keep native object ordering, and ordered sequences keep traversal order.
These operations preserve the source representation and do not mutate it.

Record and eager sequence calls execute immediately. After `LAZY`, all four
operations stream on consumption and permit downstream short-circuiting. Each
consumption creates fresh state, even after partial consumption or an error.
Whole-input distinct keeps a Set of selected values (space proportional to the
number of unique selections); adjacent distinct keeps only an initialized flag
and the previous selected value (constant state). Neither buffers all entries or
memoizes results. Lazy views remain live and repeatable; selector errors propagate
unchanged, and a later consumption starts over.

## Numeric and grouped aggregation

These terminal methods work on records, eager ordered sequences, and lazy sequences. Each call consumes pending work immediately in source order, using original record keys in callbacks. There is no hidden source cache: repeated lazy calls rerun callbacks and observe changes to the query record.

| Terminal | Result |
| --- | --- |
| `[SUM]((value, key) => number)` | Sum, starting at `+0`; empty input returns `0` |
| `[AVERAGE]((value, key) => number)` | Sum divided by count; empty input returns `undefined` |
| `[MIN]((value, key) => number)` | Minimum; empty input returns `undefined` |
| `[MAX]((value, key) => number)` | Maximum; empty input returns `undefined` |
| `[STATS]((value, key) => number)` | `NumericStats`: `{ count, sum, average, min, max }` |
| `[COUNT_BY]((value, key) => K)` | `Partial<Record<K, number>>` with counts per string group |
| `[REDUCE_BY](keyFn, initial, reducer)` | `Partial<Record<K, A>>` with one accumulator per string group |

```ts
import {
  createQueryable, SUM, AVERAGE, MIN, MAX, STATS, COUNT_BY, REDUCE_BY,
} from "@ilokesto/queryable";

const sales = createQueryable({
  alice: { team: "red", amount: 10 },
  bob: { team: "blue", amount: 20 },
  carol: { team: "red", amount: 30 },
});
sales[SUM](sale => sale.amount); // 60
sales[AVERAGE](sale => sale.amount); // 20
sales[MIN](sale => sale.amount); // 10
sales[MAX](sale => sale.amount); // 30
sales[STATS](sale => sale.amount);
// { count: 3, sum: 60, average: 20, min: 10, max: 30 }
sales[COUNT_BY](sale => sale.team); // { red: 2, blue: 1 }

const totals = sales[REDUCE_BY](
  sale => sale.team === "red" ? "red" : "blue",
  _groupKey => ({ total: 0, members: [] as string[] }),
  (acc, sale, key) => {
    acc.total += sale.amount;
    acc.members.push(key);
    return acc;
  },
);
// Partial<Record<"red" | "blue", { total: number; members: string[] }>>
totals.red?.total; // 40
```

Numeric selectors are required and return `number` only. Use custom `REDUCE` for `bigint` totals, for example `query[REDUCE]((total, value) => total + value, 0n)` on a bigint query. `STATS` makes one pass and calls the selector exactly once per entry, computing all five fields without separately consuming the source. Each individual numeric terminal also calls its selector once per entry. Empty `STATS` returns `{ count: 0, sum: 0, average: undefined, min: undefined, max: undefined }`.

Numbers use JavaScript arithmetic without filtering or coercion: sum is left-to-right `+` from `+0`, average is that sum divided by count, and extrema follow `Math.min`/`Math.max`. `NaN` propagates into numeric results but still counts as an entry. Infinities and overflow are retained; adding opposite infinities produces `NaN`. Floating-point rounding follows source order. A sum of only `-0` is `+0` (and its average is `+0`); extrema retain a lone `-0`, while mixed zero signs produce `-0` for min and `+0` for max. Even after encountering `NaN`, all remaining entries and selectors are visited unless a callback throws.

`REDUCE_BY` accepts `keyFn(value, key)`, an **initial accumulator factory** `initial(groupKey)`, and `reducer(accumulator, value, key)`, in that argument order so the factory infers the reducer's accumulator type. For each entry it calls the key function, creates the accumulator if this is the first entry in that group, then invokes the reducer, including on the first entry. The factory runs exactly once per encountered group per terminal call, never for absent groups or empty input. Return a fresh object from the factory when groups need separate mutable state. The reducer's returned value replaces that group's accumulator, including `undefined`, `null`, `false`, `0`, and `""`; a stored `undefined` never reinitializes a group.

Both grouped terminals fold directly without retaining full groups. Their result has a null prototype, so `""`, `__proto__`, `constructor`, and `toString` are safe string group keys. Literal key unions remain inferred, but each property is optional because the group may be absent; use `Object.hasOwn(result, key)` to distinguish an absent group from a present `undefined` accumulator. Output property enumeration follows native object ordering, including integer-like keys. Within each group reducers see the stable source order. Errors from upstream work, selectors, factories, and reducers propagate immediately; later lazy consumption starts a fresh traversal and creates fresh accumulators.

`GROUP_BY` remains different: it eagerly materializes full snapshot groups that can be queried further. Use it when group contents are needed; use `COUNT_BY` or `REDUCE_BY` when only a per-group count or fold is needed.

## Lookup and default reads

These shared terminal methods work on records, ordered sequences, and lazy views in query order.

| Operation | Result |
| --- | --- |
| `[LAST]()` | Last value, or `undefined` when empty |
| `[AT](index)` | Value at a zero-based index; negative indexes count from the end |
| `[SINGLE](predicate?)` | Only matching value, or `undefined` for no match; throws `RangeError` on the second match |
| `[EVERY](predicate)` | Whether every value matches; `true` when empty |
| `[IS_EMPTY]()` | Whether no entry exists |
| `[INCLUDES](value)` | Whether a value exists using SameValueZero (`NaN` matches `NaN`, `0` matches `-0`, objects use identity) |
| `[FIND_ENTRY](predicate)` | First matching fresh `[key, value]` tuple, or `undefined` |
| `[FIRST_OR](value)` | First value, using the supplied fallback only when empty |
| `[FIRST_OR_ELSE](factory)` | First value, calling the zero-argument factory exactly once only when empty |

Predicates receive `(value, key)`. `SINGLE` without a predicate counts every entry; with a predicate it counts only matches. A stored `undefined` is still a match and a second such entry still throws. `SINGLE` and `FIND_ENTRY` preserve type guard narrowing. Returned tuples are fresh but their values remain shared references.

`AT` uses `Array.at` numeric coercion: fractions truncate toward zero, `NaN` selects index zero, and signed zero selects the first entry. Both infinities return `undefined` without iterating or executing pending lazy callbacks. Coercion errors propagate before iteration. A finite nonnegative index stops at the selected entry (or exhausts the query when out of range). A finite negative index consumes the whole query and buffers at most `min(entry count, abs(truncated index))` values. `LAST` also consumes the whole query. `SINGLE` consumes until exhaustion or its second match; the other reads stop as soon as their result is known. Repeated calls on lazy views repeat pending work.

Presence never depends on truthiness or on whether a value is `undefined`. Existing `FIRST` and `FIND` still return `undefined` for either absence or a stored `undefined`; default reads instead inspect entry presence and keep stored `0`, `false`, and `undefined` unchanged. Predicate and factory errors propagate unchanged.

```ts
import {
  createQueryable, AT, FIND_ENTRY, FIRST_OR, FIRST_OR_ELSE, SINGLE,
} from "@ilokesto/queryable";

const query = createQueryable<number | string | undefined>({ a: undefined, b: 0, c: "three" });
query[FIRST_OR](99); // undefined: entry "a" exists
query[FIRST_OR_ELSE](() => 99); // undefined: factory is not called
query[AT](-1); // "three"
query[SINGLE]((value): value is string => typeof value === "string"); // string | undefined
query[FIND_ENTRY]((value): value is string => typeof value === "string"); // [string, string] | undefined
```

## Bounds and prefixes

These shared Symbol operations retain original keys and query mode: records return records, and ordered or lazy sequences return sequences. They execute immediately on eager queries and defer work on lazy queries.

| Operation | Result |
| --- | --- |
| `[SKIP](n)` | Exclude the first `n` entries |
| `[TAKE_WHILE]((value, key) => boolean)` | Keep the matching prefix, excluding the first mismatch |
| `[DROP_WHILE]((value, key) => boolean)` | Exclude the matching prefix, including the first mismatch in the result |
| `[TAKE_LAST](n)` | Keep the last `n` entries in input order |
| `[DROP_LAST](n)` | Exclude the last `n` entries in input order |

All three numeric bounds use the same size normalization: truncate fractions toward zero, clamp negative sizes (including `-Infinity`) to zero, treat `NaN` as zero, and retain `Infinity`. Thus `SKIP(0)` and `DROP_LAST(0)` keep everything, while `TAKE_LAST(0)` is empty and does not read upstream. This does not change the signed `slice(0, n)` contract of `LIMIT`.

```ts
import {
  createQueryable, LAZY, SKIP, LIMIT, TAKE_WHILE, DROP_WHILE,
  TAKE_LAST, DROP_LAST, VALUES,
} from "@ilokesto/queryable";

const query = createQueryable({ a: 1, b: 2, c: 3, d: 2 });
query[LAZY]()[SKIP](1)[LIMIT](2)[VALUES](); // [2, 3]
query[TAKE_WHILE](n => n < 3)[VALUES](); // [1, 2]
query[DROP_WHILE](n => n < 3)[VALUES](); // [3, 2]
query[TAKE_LAST](2)[VALUES](); // [3, 2]
query[DROP_LAST](2)[VALUES](); // [1, 2]
```

Use `SKIP(start)[LIMIT](length)` for a nonnegative window; there is no separate `SLICE` operation. Integer record keys still follow native object ordering; sequence keys retain their upstream order. Stored `undefined` and special keys are retained normally.

`TAKE_WHILE` stops at the first mismatch and supports type guards. `DROP_WHILE` stops calling its predicate after the first mismatch; its remaining values are not narrowed. Both predicates receive the original key.

On lazy queries, `SKIP(n)[FIRST]()` pulls at most `n + 1` entries and `TAKE_WHILE(predicate)[LIMIT](k)` stops after the required prefix without testing a later entry. `TAKE_LAST(n)` must finish upstream before yielding anything and stores at most `n` entries in a ring buffer for finite sizes. `DROP_LAST(n)` uses at most `n` buffered entries and needs `n + 1` upstream entries for its first output; early terminals can then stop it. Neither operation moves ahead of sorting, sequence `PICK`, or negative `LIMIT` barriers.

`SKIP(Infinity)` and `DROP_LAST(Infinity)` consume upstream and return no entries; the latter stores none. `TAKE_LAST(Infinity)` consumes and buffers the entire input before returning all entries. Each consumption gets fresh counters, predicate state, and buffers, including after early termination or an error. Lazy callbacks and errors remain deferred, and mutations between consumptions remain visible.

## Iterable sources and key identity

`createQuerySequence(factory, options?)` creates a lazy sequence from a factory of
`Iterable<readonly [string, T]>`. Construction does not call the factory. Each
consumption calls it again: return a fresh iterator or a repeatable iterable, not
the same exhausted generator. There is no result cache or automatic rewind.

```ts
import { createQuerySequence, iterateEntries, iterateValues } from "@ilokesto/queryable";

const rows = new Map([["2", 20], ["1", 10]]);
const query = createQuerySequence(() => rows.entries());
const entries = iterateEntries(query); // no consumption yet
[...entries]; // [["2", 20], ["1", 10]]
rows.set("2", 30);
[...iterateValues(query)]; // [30, 10]
```

`iterateEntries(query)` and `iterateValues(query)` accept records and sequences
without first collecting an array. Each iterator is independent. Entry views
return fresh mutable tuples; changing them does not change a buffered query.
Values remain shallow references. A query itself has no ambiguous default
iterator: choose entries or values explicitly.

External entries must be two-element arrays with string keys. Values, including
`undefined`, Symbols, and opaque objects, are not inspected. Malformed entries
throw `TypeError` when pulled. Acquired generators close on early exit or a
downstream error; `LIMIT(0)` does not acquire the source.

The `duplicateKeys` option makes key collisions explicit:

| Policy | Behavior |
| --- | --- |
| `"error"` (default) | Throw `DuplicateKeyError`, whose `key` identifies the repeated key, when that entry is pulled |
| `"first"` | Keep the first value, including a stored `undefined`; later occurrences are skipped |
| `"last"` | Consume the whole source before yielding; use the last value while keeping each key's first position |

Every consumption creates fresh identity state. The streaming policies retain a
set of observed keys; `"last"` buffers a map of all distinct keys. Prefix
consumers validate only what they pull, not the unconsumed tail. Full consumers
therefore reject duplicate keys by default instead of silently overwriting them.
`PICK`, grouping, sorting, and collection outputs receive the same unique-key
entries. This is also the identity boundary for future multi-source operations.
`TO_OBJECT` still intentionally restores native object ordering for integer keys.

## Local entry buffers and adjacent groups

These shared Symbol methods return ordered `QuerySequence` results. Each result
key is the original key of its first included entry (its anchor), never a
generated index or a selector result. Unique input keys therefore give unique
anchors, including numeric and special keys. Each value is a fresh mutable array
of fresh `[originalKey, value]` tuples; nested values remain shallow references.
Overlapping windows do not share exposed tuples. Later pulls and repeated
consumption do not modify previously returned buffers, and editing an exposed
buffer does not edit retained eager snapshots.

| Method | Buffer policy |
| --- | --- |
| `[CHUNK](size)` | Nonoverlapping batches; include the final nonempty partial chunk |
| `[WINDOW](size, stride = 1, partial = false)` | Start at positions `0, stride, 2 * stride, ...`; overlap when stride is smaller than size, skip gaps when larger; emit only full windows unless partial is true |
| `[PAIRWISE]()` | Complete overlapping pairs; `EntryPair<T>` is exactly `[[string, T], [string, T]]` |
| `[SPLIT]((value, originalKey) => boolean)` | Matching entries are delimiters and are excluded; leading, repeated, and trailing delimiters never produce empty groups |
| `[PARTITION_BY]((value, originalKey) => selected)` | Emit consecutive runs of equal selector results; include the final nonempty run |

`size` and `stride` must be positive finite integers; invalid arguments throw
`RangeError` immediately, even on a lazy or empty query, before acquiring input.
Empty input yields no buffers. A short input yields a partial CHUNK, no default
WINDOW or PAIRWISE, and a partial WINDOW only when requested. With partial windows
enabled, every start position before the end can yield a nonempty trailing
window, including multiple shrinking overlapping tails.

```ts
import {
  createQueryable, LAZY, CHUNK, WINDOW, PAIRWISE, SPLIT, PARTITION_BY, ENTRIES, VALUES,
} from "@ilokesto/queryable";

const query = createQueryable({ a: 1, b: 1, c: 2, d: 1 });
query[CHUNK](3)[ENTRIES]();
// [["a", [["a", 1], ["b", 1], ["c", 2]]], ["d", [["d", 1]]]]
query[WINDOW](2, 3, true)[VALUES]();
// [[["a", 1], ["b", 1]], [["d", 1]]]
query[PAIRWISE]()[VALUES](); // three complete pairs of original entries
query[LAZY]()[SPLIT](value => value === 2)[VALUES]();
// [[["a", 1], ["b", 1]], [["d", 1]]]
query[LAZY]()[PARTITION_BY](value => value)[VALUES]();
// [[["a", 1], ["b", 1]], [["c", 2]], [["d", 1]]]
```

PARTITION_BY uses the SameValueZero equality contract of Set-based DISTINCT_BY:
`NaN` equals `NaN`, `-0` equals `0`, and objects and Symbols compare by identity.
Stored `undefined` and an `undefined` selector result are ordinary data, not
missing-state sentinels. `A,A,B,A` forms three runs, unlike eager GROUP_BY, which
still collects all equal string group keys together.

On records and eager sequences these methods execute immediately and return
snapshots. After LAZY they defer execution, read the live source again on each
consumption, and create independent buffer state without memoization. Callbacks
run once per pulled entry in source order with `(value, originalKey)`. SPLIT
reads through the delimiter ending a group. PARTITION_BY must select one entry
past a run to discover its boundary; that entry starts the next run without a
second selector call. At source exhaustion no extra callback runs. Early exit
and callback or source failures close acquired upstream generators; errors
propagate unchanged and the next consumption starts fresh.

Lazy CHUNK/WINDOW retain at most `size` original entries internally; PAIRWISE
retains one previous entry. Fresh emitted copies also cost space proportional to
the emitted buffer. SPLIT and PARTITION_BY may retain an unbounded current group
until a delimiter, a changed selector, or source exhaustion arrives; they cannot
produce a group from an infinite uninterrupted run. These bounds exclude
upstream identity tracking, buffering operators, and results retained by the
consumer. Eager evaluation necessarily stores all resulting buffers.

### Async entry sources and Promise normalization

`createAsyncQuerySequence(factory, options?)` is a separate, always-deferred
`AsyncQuerySequence<Awaited<T>>`. Its `AsyncEntrySourceFactory<T>` returns an
`Iterable<readonly [string, T]>`, an `AsyncIterable<readonly [string, T]>`, or a
PromiseLike of either. Construction and chain operations do not acquire the
source. Each consumption calls the factory again; return a fresh iterator or a
repeatable iterable. `LAZY` remains live, repeatable, and nonmemoized.

```ts
import {
  createAsyncQuerySequence, iterateAsyncEntries, MAP, WHERE, LIMIT, VALUES, GROUP_BY,
} from "@ilokesto/queryable";

const rows = new Map([["2", Promise.resolve(20)], ["1", Promise.resolve(10)]]);
const query = createAsyncQuerySequence(() => rows.entries())
  [MAP](async (value, key) => ({ key, doubled: value * 2 }))
  [WHERE](async value => value.doubled >= 20);
const values = await query[LIMIT](1)[VALUES](); // [{ key: "2", doubled: 40 }]
for await (const [key, value] of iterateAsyncEntries(query)) {
  // Explicit entry view; a break closes upstream.
}
const groups = await query[GROUP_BY](async value => value.doubled > 20 ? "high" : "low");
const high = await groups.high?.[VALUES]();
```

- Source values and `MAP` results are intentionally awaited, recursively through
  PromiseLike layers. Plain, Promise, mixed, `never`, and `undefined` types use
  `Awaited` inference. This is not opaque Promise storage: a value's `then`
  property may be read, and a rejection propagates. Properties inside a normal
  value object are not recursively traversed. Synchronous queries still store
  Promises and other values unchanged.
- `MAP`, `WHERE`, `FIND`, `SOME`, and `GROUP_BY` callbacks receive
  `(awaitedValue, originalKey)` in source order. Predicates and grouping callbacks
  may return PromiseLike results. Each callback completes before the next entry
  is requested; there is no concurrent work or prefetch. Synchronous type guards
  narrow `WHERE`/`FIND`; async boolean predicates do not.
- `COUNT`, `FIRST`, `VALUES`, `ENTRIES`, `FIND`, and `SOME` explicitly return
  Promises. Empty results are respectively `0`, `undefined`, a fresh empty array,
  a fresh empty array, `undefined`, and `false`, without invoking callbacks.
  Stored `undefined` still counts as an entry.
- `iterateAsyncEntries(query)` and `iterateAsyncValues(query)` return explicit,
  repeatable async iterable views, with independent cursors and fresh entry
  tuples. The query has no default iterator. Methods use the existing Symbols on
  one frozen shared async prototype, separate from the synchronous prototype.
- `SORT` defers a full buffer until consumption and takes a synchronous
  `(leftValue, rightValue) => number` comparator. Ties stay stable; numeric and
  special keys retain sequence order. `LIMIT` keeps the same `slice(0, n)`
  semantics, including finite-negative buffering and no acquisition for an empty
  limit. `FIRST`, `FIND`, `SOME`, and positive `LIMIT` short-circuit.
- `GROUP_BY` starts consumption when called, not when its returned Promise is
  awaited. Awaiting it finishes all grouping callbacks and returns
  `Partial<Record<K, AsyncQuerySequence<T>>>` snapshot groups. Reconsuming a group
  does not rerun the original source or grouping callback. Each group's entries
  keep input order; the null-prototype group record uses native object key order
  and safely supports `__proto__`/`constructor`. Further group transformations are
  deferred async operations.
- `duplicateKeys: "error" | "first" | "last"` uses the same identity rules and
  `DuplicateKeyError` as sync factories. Every pulled value is awaited, including
  duplicates later skipped by `"first"`. `"last"` buffers before yielding, with
  last values in first-key positions. Identity state is fresh per consumption;
  prefix consumers check only pulled entries.
- The source protocol closes an acquired, unfinished iterator exactly once on
  rejected `next()`, rejected values/callbacks, or early exit, and awaits its
  `return()` before settling. Natural exhaustion does not call `return()`.
  An existing failure keeps its identity if cleanup also fails; otherwise cleanup
  failure rejects the terminal or view. Factory errors reject consumption; the
  next consumption tries a fresh factory call. Sources must implement `return()`
  to release resources. Cancellation, finalization hooks, concurrency, retries,
  and events are not part of this async foundation.

## Native collection outputs and Map-key groups

`KEYS()` returns a fresh string array in query order. `TO_MAP()` returns a fresh
`Map<string, T>` of original keys and shallow values, including stored
`undefined`. `TO_SET()` collects values in first-occurrence order using native
SameValueZero equality: `NaN` matches itself, `-0` matches `0`, and objects use
reference identity. These terminals consume the query; lazy work runs again
on every call. Changing a returned collection does not modify the source.

`GROUP_BY_MAP((value, originalKey) => groupKey)` accepts arbitrary group keys:
objects, Symbols, numbers, `undefined`, and other native Map keys. It calls the
selector once per entry and eagerly materializes independent groups even on
lazy input. Map iteration follows the first occurrence of each group key.
Members retain original keys and input order (native object order for record
groups, sequence order for ordered/lazy groups). Values remain shallow references.

```ts
import { createQueryable, GROUP_BY_MAP, KEYS, TO_MAP, TO_SET } from "@ilokesto/queryable";

const team = {};
const users = createQueryable({ alice: { team }, bob: { team } });
const groups = users[GROUP_BY_MAP](user => user.team);
groups.get(team)?.[KEYS](); // ["alice", "bob"]
users[TO_MAP]().get("alice"); // { team }
users[TO_SET]().size; // 2: distinct user objects
```

Group keys are never stringified or exposed as record keys. The returned Map
is not a query and has no implicit JSON/object conversion; explicitly choose a
serialization representation. Existing string-keyed `GROUP_BY` remains unchanged.
Empty inputs return fresh empty collections. Factory-source duplicate policies
still apply before these operations, so default duplicate keys throw rather
than silently overwrite values in `TO_MAP`.

## Async cancellation and lifetime hooks

Pass `{ signal }` to `createAsyncQuerySequence`. The factory receives that signal;
async `MAP`, `WHERE`, `FIND`, `SOME`, `GROUP_BY`, and the synchronous `SORT`
comparator receive it after their existing arguments. It can be `undefined`.
Callbacks and factories with fewer arguments continue to work.

```ts
import { createAsyncQuerySequence, FINALIZE, MAP, ON_COMPLETE, VALUES } from "@ilokesto/queryable";

const controller = new AbortController();
const query = createAsyncQuerySequence(
  signal => [["a", signal?.aborted ? 0 : 1]],
  { signal: controller.signal },
)[MAP](async (value, key, signal) => value + key.length)
  [ON_COMPLETE](() => { console.log("upstream exhausted"); })
  [FINALIZE](outcome => { console.log(outcome.reason); });
await query[VALUES](); // [2]
```

An already-aborted signal rejects with its exact `reason` before factory
acquisition. Abort also interrupts pending factory, `next`, value, and callback
waits. Each wait removes its abort listener when settled; late external
rejections remain handled. A consumed sequence with the same aborted signal
rejects again; create a new controller/query to start a new lifetime.
Buffered SORT, negative LIMIT, `"last"` collision results, and snapshot groups
check cancellation before each output, including after a comparator aborts.

Cancellation stops consumption, not arbitrary external work. Pass the received
signal to that work for cooperative cancellation. On abort, an acquired iterator's
`return()` is attempted once without waiting for a non-cooperative pending
`next()` to release its queue. Its later cleanup rejection cannot replace the
abort reason. Other exits await iterator cleanup. Native async generators may
therefore finish external cleanup later if their pending work ignores the signal.

`FINALIZE((outcome, signal) => ...)` is awaited once per started consumption,
including early return and error. `ConsumptionOutcome` is `"complete"` or
`"return"`, or `"error"`/`"abort"` with an `error` field. This describes the
hook's upstream stage: a downstream failure closes it as a return, while a
failure inside its upstream is observable as an error. Place hooks accordingly.
An existing upstream error/abort wins over a finalizer failure; without a primary
failure, cleanup failure rejects the consumer. Finalizers must settle for the
consumer to settle.

`ON_COMPLETE(callback)` runs only after its own upstream exhausts normally, not
after early return or failure. For example, a hook after `LIMIT(1)` sees that
limited stage complete; a hook before it sees early return. No hook or source
runs for an unused query or a downstream `LIMIT(0)`. All hook methods remain
shared and frozen, with fresh execution state on each consumption.
