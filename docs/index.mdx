# Queryable

Version **0.0.1**, private beta. Unpublished on npm; the local documentation site covers the `next` channel only.

```ts
import { createQueryable, WHERE, SORT, LIMIT, MAP, VALUES } from "@ilokesto/queryable";

const users = createQueryable({
  alice: { name: "Alice", age: 25 },
  bob: { name: "Bob", age: 30 },
  charlie: { name: "Charlie", age: 20 },
});

const names = users
  [WHERE](user => user.age >= 25)
  [SORT]((a, b) => b.age - a.age)
  [LIMIT](2)
  [MAP](user => user.name)
  [VALUES](); // ["Bob", "Alice"]
```

## Operations

| Operation | Result |
| --- | --- |
| `[WHERE]((value, key) => boolean)` | Matching records; type guards narrow the value type |
| `[SORT]((a, b) => number)` | Stable ordered `QuerySequence`, including numeric keys |
| `[MAP]((value, key) => next)` | Transformed values with original record keys |
| `[PICK](...keys)` | Whole values for existing **record keys**; missing/duplicate keys ignored |
| `[LIMIT](n)` | Entries selected by `slice(0, n)` |
| `[GROUP_BY]((value, key) => K)` | Materialized groups; `Partial<Record<K, ...>>` preserves literal keys |
| `[COUNT]()` | Number of records |
| `[FIRST]()` | First value or `undefined` |
| `[VALUES]()` | Fresh value array |
| `[FIND]((value, key) => boolean)` | First matching value, with type guard narrowing, or `undefined` |
| `[SOME]((value, key) => boolean)` | Boolean; stops on the first match |
| `[ENTRIES]()` | Fresh `[key, value]` tuples in query order |
| `[TO_OBJECT]()` | Ordinary shallow object, without query methods |
| `[REDUCE]((acc, value, key) => next, initial)` | Fold in query order; initial is required |
| `[LAZY]()` | Repeatable, non-memoized deferred sequence |

## Records, ordering, and migration

`createQueryable` returns a mutable `Queryable<T>` record. Its eager `WHERE`, `MAP`, `PICK`, and `LIMIT` return new records. `SORT` returns `QuerySequence<T>`: ordered entries rather than a record whose numeric keys could reorder themselves. Subsequent transformations keep the sequence representation. Use `VALUES` or `ENTRIES` to preserve order; `TO_OBJECT` intentionally restores native object key ordering. Do not use record indexing, object spread, or JSON on sequences to extract their data.

```ts
import { createQueryable, SORT, LIMIT, ENTRIES, TO_OBJECT } from "@ilokesto/queryable";

const sorted = createQueryable({ 1: 10, 2: 20 })[SORT]((a, b) => b - a);
sorted[LIMIT](1)[ENTRIES](); // [["2", 20]]
sorted[TO_OBJECT](); // ordinary object; numeric keys enumerate as "1", "2"
```

This private beta intentionally removes `SELECT`: rename imports and calls to `PICK`. It still selects **record keys**, not fields inside values. Use `MAP(user => ({ name: user.name }))` for field projection. Record `PICK` uses argument insertion order subject to native numeric-key ordering; sequence `PICK` preserves argument order exactly.

## Lazy evaluation and short-circuiting

```ts
import { createQueryable, LAZY, WHERE, MAP, LIMIT, VALUES } from "@ilokesto/queryable";

const query = createQueryable({ a: 1, b: 2, c: 3, d: 4 });
const firstEven = query[LAZY]()
  [WHERE](n => n % 2 === 0)
  [MAP](n => n * 10)
  [LIMIT](1);
firstEven[VALUES](); // [20]; only a and b reach the predicate
```

- Eager queries run callbacks when an operation is called. `LAZY` defers subsequent `WHERE`, `MAP`, `PICK`, `LIMIT`, and `SORT` until a terminal call.
- `VALUES`, `ENTRIES`, `TO_OBJECT`, `COUNT`, `REDUCE`, `FIRST`, `FIND`, `SOME`, and `GROUP_BY` consume pending work. `FIRST`, `FIND`, `SOME`, and nonnegative `LIMIT` can stop upstream iteration early; `LIMIT(0)` never consumes the source.
- `SORT`, sequence `PICK`, and finite negative `LIMIT` need the full upstream input. They buffer on consumption. `GROUP_BY` always executes immediately and returns eager snapshot groups: records for record queries, sequences for sequence queries.
- Each consumption starts fresh and reruns deferred callbacks. There is no cache. Errors propagate at consumption, and another consumption starts a fresh attempt.
- A record's lazy view reads that **query record** at consumption, so mutations between consumptions are visible. Changes to the original input object are not: construction already shallow-copied it. An eager sorted sequence is a snapshot; adding `LAZY` afterward does not rerun its already executed sort.
- Values are shallow references, not deeply frozen. Callbacks should not add, delete, or replace source records during a traversal; mutation during traversal is not a snapshot-isolation contract.

For a single lookup, prefer `query[FIND](predicate)` or `query[SOME](predicate)`. `query[WHERE](predicate)[FIRST]()` still eagerly builds the entire filtered record.

## Types and aggregation

```ts
import { createQueryable, WHERE, GROUP_BY, REDUCE } from "@ilokesto/queryable";

const mixed = createQueryable<number | string>({ a: 1, b: "two" });
const strings = mixed[WHERE]((value): value is string => typeof value === "string");
// Queryable<string>
const groups = createQueryable({ a: 1, b: 2, c: 3 })
  [GROUP_BY](n => n % 2 ? "odd" : "even");
const oddTotal = groups.odd?.[REDUCE]((sum, n) => sum + n, 0); // 4
// A possible group key may be absent, including for empty input.
```

## Contract and limitations

- Own enumerable string keys are data. Inherited, non-enumerable, and Symbol-keyed input properties are not copied. `__proto__`, `constructor`, and `toString` are supported as ordinary data keys; the shared prototype has a null root.
- Construction and query operations make shallow copies. Values remain shared references. Queries are mutable records, but operations do not mutate their source.
- `LIMIT` retains native `slice` semantics: negative numbers drop trailing entries, fractions truncate, `NaN` gives an empty result, and `Infinity` keeps all entries.
- Methods need their receiver: call `query[WHERE](predicate)`, not a detached method. Object spread and JSON on records retain data but lose query methods.
- Methods are shared and frozen, not bound per instance. This is a structural allocation choice, not a promise of a particular heap reduction or runtime speed.

## Iterable sources and key identity

`createQuerySequence(factory, options?)` creates a lazy sequence from a factory of
`Iterable<readonly [string, T]>`. Construction does not call the factory. Each
consumption calls it again: return a fresh iterator or a repeatable iterable, not
the same exhausted generator. There is no result cache or automatic rewind.

```ts
import { createQuerySequence, iterateEntries, iterateValues } from "@ilokesto/queryable";

const rows = new Map([["2", 20], ["1", 10]]);
const query = createQuerySequence(() => rows.entries());
const entries = iterateEntries(query); // no consumption yet
[...entries]; // [["2", 20], ["1", 10]]
rows.set("2", 30);
[...iterateValues(query)]; // [30, 10]
```

`iterateEntries(query)` and `iterateValues(query)` accept records and sequences
without first collecting an array. Each iterator is independent. Entry views
return fresh mutable tuples; changing them does not change a buffered query.
Values remain shallow references. A query itself has no ambiguous default
iterator: choose entries or values explicitly.

External entries must be two-element arrays with string keys. Values, including
`undefined`, Symbols, and opaque objects, are not inspected. Malformed entries
throw `TypeError` when pulled. Acquired generators close on early exit or a
downstream error; `LIMIT(0)` does not acquire the source.

The `duplicateKeys` option makes key collisions explicit:

| Policy | Behavior |
| --- | --- |
| `"error"` (default) | Throw `DuplicateKeyError`, whose `key` identifies the repeated key, when that entry is pulled |
| `"first"` | Keep the first value, including a stored `undefined`; later occurrences are skipped |
| `"last"` | Consume the whole source before yielding; use the last value while keeping each key's first position |

Every consumption creates fresh identity state. The streaming policies retain a
set of observed keys; `"last"` buffers a map of all distinct keys. Prefix
consumers validate only what they pull, not the unconsumed tail. Full consumers
therefore reject duplicate keys by default instead of silently overwriting them.
`PICK`, grouping, sorting, and collection outputs receive the same unique-key
entries. This is also the identity boundary for future multi-source operations.
`TO_OBJECT` still intentionally restores native object ordering for integer keys.

### Async entry sources and Promise normalization

`createAsyncQuerySequence(factory, options?)` is a separate, always-deferred
`AsyncQuerySequence<Awaited<T>>`. Its `AsyncEntrySourceFactory<T>` returns an
`Iterable<readonly [string, T]>`, an `AsyncIterable<readonly [string, T]>`, or a
PromiseLike of either. Construction and chain operations do not acquire the
source. Each consumption calls the factory again; return a fresh iterator or a
repeatable iterable. `LAZY` remains live, repeatable, and nonmemoized.

```ts
import {
  createAsyncQuerySequence, iterateAsyncEntries, MAP, WHERE, LIMIT, VALUES, GROUP_BY,
} from "@ilokesto/queryable";

const rows = new Map([["2", Promise.resolve(20)], ["1", Promise.resolve(10)]]);
const query = createAsyncQuerySequence(() => rows.entries())
  [MAP](async (value, key) => ({ key, doubled: value * 2 }))
  [WHERE](async value => value.doubled >= 20);
const values = await query[LIMIT](1)[VALUES](); // [{ key: "2", doubled: 40 }]
for await (const [key, value] of iterateAsyncEntries(query)) {
  // Explicit entry view; a break closes upstream.
}
const groups = await query[GROUP_BY](async value => value.doubled > 20 ? "high" : "low");
const high = await groups.high?.[VALUES]();
```

- Source values and `MAP` results are intentionally awaited, recursively through
  PromiseLike layers. Plain, Promise, mixed, `never`, and `undefined` types use
  `Awaited` inference. This is not opaque Promise storage: a value's `then`
  property may be read, and a rejection propagates. Properties inside a normal
  value object are not recursively traversed. Synchronous queries still store
  Promises and other values unchanged.
- `MAP`, `WHERE`, `FIND`, `SOME`, and `GROUP_BY` callbacks receive
  `(awaitedValue, originalKey)` in source order. Predicates and grouping callbacks
  may return PromiseLike results. Each callback completes before the next entry
  is requested; there is no concurrent work or prefetch. Synchronous type guards
  narrow `WHERE`/`FIND`; async boolean predicates do not.
- `COUNT`, `FIRST`, `VALUES`, `ENTRIES`, `FIND`, and `SOME` explicitly return
  Promises. Empty results are respectively `0`, `undefined`, a fresh empty array,
  a fresh empty array, `undefined`, and `false`, without invoking callbacks.
  Stored `undefined` still counts as an entry.
- `iterateAsyncEntries(query)` and `iterateAsyncValues(query)` return explicit,
  repeatable async iterable views, with independent cursors and fresh entry
  tuples. The query has no default iterator. Methods use the existing Symbols on
  one frozen shared async prototype, separate from the synchronous prototype.
- `SORT` defers a full buffer until consumption and takes a synchronous
  `(leftValue, rightValue) => number` comparator. Ties stay stable; numeric and
  special keys retain sequence order. `LIMIT` keeps the same `slice(0, n)`
  semantics, including finite-negative buffering and no acquisition for an empty
  limit. `FIRST`, `FIND`, `SOME`, and positive `LIMIT` short-circuit.
- `GROUP_BY` starts consumption when called, not when its returned Promise is
  awaited. Awaiting it finishes all grouping callbacks and returns
  `Partial<Record<K, AsyncQuerySequence<T>>>` snapshot groups. Reconsuming a group
  does not rerun the original source or grouping callback. Each group's entries
  keep input order; the null-prototype group record uses native object key order
  and safely supports `__proto__`/`constructor`. Further group transformations are
  deferred async operations.
- `duplicateKeys: "error" | "first" | "last"` uses the same identity rules and
  `DuplicateKeyError` as sync factories. Every pulled value is awaited, including
  duplicates later skipped by `"first"`. `"last"` buffers before yielding, with
  last values in first-key positions. Identity state is fresh per consumption;
  prefix consumers check only pulled entries.
- The source protocol closes an acquired, unfinished iterator exactly once on
  rejected `next()`, rejected values/callbacks, or early exit, and awaits its
  `return()` before settling. Natural exhaustion does not call `return()`.
  An existing failure keeps its identity if cleanup also fails; otherwise cleanup
  failure rejects the terminal or view. Factory errors reject consumption; the
  next consumption tries a fresh factory call. Sources must implement `return()`
  to release resources. Cancellation, finalization hooks, concurrency, retries,
  and events are not part of this async foundation.
