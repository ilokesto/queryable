# Queryable

Version **0.0.1**, private beta. Unpublished on npm; the local documentation site covers the `next` channel only.

```ts
import { createQueryable, WHERE, SORT, LIMIT, MAP, VALUES } from "@ilokesto/queryable";

const users = createQueryable({
  alice: { name: "Alice", age: 25 },
  bob: { name: "Bob", age: 30 },
  charlie: { name: "Charlie", age: 20 },
});

const names = users
  [WHERE](user => user.age >= 25)
  [SORT]((a, b) => b.age - a.age)
  [LIMIT](2)
  [MAP](user => user.name)
  [VALUES](); // ["Bob", "Alice"]
```

## Operations

| Operation | Result |
| --- | --- |
| `[WHERE]((value, key) => boolean)` | Matching records; type guards narrow the value type |
| `[SORT]((a, b) => number)` | Stable ordered `QuerySequence`, including numeric keys |
| `[MAP]((value, key) => next)` | Transformed values with original record keys |
| `[PICK](...keys)` | Whole values for existing **record keys**; missing/duplicate keys ignored |
| `[LIMIT](n)` | Entries selected by `slice(0, n)` |
| `[GROUP_BY]((value, key) => K)` | Materialized groups; `Partial<Record<K, ...>>` preserves literal keys |
| `[COUNT]()` | Number of records |
| `[FIRST]()` | First value or `undefined` |
| `[VALUES]()` | Fresh value array |
| `[FIND]((value, key) => boolean)` | First matching value, with type guard narrowing, or `undefined` |
| `[SOME]((value, key) => boolean)` | Boolean; stops on the first match |
| `[ENTRIES]()` | Fresh `[key, value]` tuples in query order |
| `[TO_OBJECT]()` | Ordinary shallow object, without query methods |
| `[REDUCE]((acc, value, key) => next, initial)` | Fold in query order; initial is required |
| `[LAZY]()` | Repeatable, non-memoized deferred sequence |

## Records, ordering, and migration

`createQueryable` returns a mutable `Queryable<T>` record. Its eager `WHERE`, `MAP`, `PICK`, and `LIMIT` return new records. `SORT` returns `QuerySequence<T>`: ordered entries rather than a record whose numeric keys could reorder themselves. Subsequent transformations keep the sequence representation. Use `VALUES` or `ENTRIES` to preserve order; `TO_OBJECT` intentionally restores native object key ordering. Do not use record indexing, object spread, or JSON on sequences to extract their data.

```ts
import { createQueryable, SORT, LIMIT, ENTRIES, TO_OBJECT } from "@ilokesto/queryable";

const sorted = createQueryable({ 1: 10, 2: 20 })[SORT]((a, b) => b - a);
sorted[LIMIT](1)[ENTRIES](); // [["2", 20]]
sorted[TO_OBJECT](); // ordinary object; numeric keys enumerate as "1", "2"
```

This private beta intentionally removes `SELECT`: rename imports and calls to `PICK`. It still selects **record keys**, not fields inside values. Use `MAP(user => ({ name: user.name }))` for field projection. Record `PICK` uses argument insertion order subject to native numeric-key ordering; sequence `PICK` preserves argument order exactly.

## Lazy evaluation and short-circuiting

```ts
import { createQueryable, LAZY, WHERE, MAP, LIMIT, VALUES } from "@ilokesto/queryable";

const query = createQueryable({ a: 1, b: 2, c: 3, d: 4 });
const firstEven = query[LAZY]()
  [WHERE](n => n % 2 === 0)
  [MAP](n => n * 10)
  [LIMIT](1);
firstEven[VALUES](); // [20]; only a and b reach the predicate
```

- Eager queries run callbacks when an operation is called. `LAZY` defers subsequent `WHERE`, `MAP`, `PICK`, `LIMIT`, and `SORT` until a terminal call.
- `VALUES`, `ENTRIES`, `TO_OBJECT`, `COUNT`, `REDUCE`, `FIRST`, `FIND`, `SOME`, and `GROUP_BY` consume pending work. `FIRST`, `FIND`, `SOME`, and nonnegative `LIMIT` can stop upstream iteration early; `LIMIT(0)` never consumes the source.
- `SORT`, sequence `PICK`, and finite negative `LIMIT` need the full upstream input. They buffer on consumption. `GROUP_BY` always executes immediately and returns eager snapshot groups: records for record queries, sequences for sequence queries.
- Each consumption starts fresh and reruns deferred callbacks. There is no cache. Errors propagate at consumption, and another consumption starts a fresh attempt.
- A record's lazy view reads that **query record** at consumption, so mutations between consumptions are visible. Changes to the original input object are not: construction already shallow-copied it. An eager sorted sequence is a snapshot; adding `LAZY` afterward does not rerun its already executed sort.
- Values are shallow references, not deeply frozen. Callbacks should not add, delete, or replace source records during a traversal; mutation during traversal is not a snapshot-isolation contract.

For a single lookup, prefer `query[FIND](predicate)` or `query[SOME](predicate)`. `query[WHERE](predicate)[FIRST]()` still eagerly builds the entire filtered record.

## Types and aggregation

```ts
import { createQueryable, WHERE, GROUP_BY, REDUCE } from "@ilokesto/queryable";

const mixed = createQueryable<number | string>({ a: 1, b: "two" });
const strings = mixed[WHERE]((value): value is string => typeof value === "string");
// Queryable<string>
const groups = createQueryable({ a: 1, b: 2, c: 3 })
  [GROUP_BY](n => n % 2 ? "odd" : "even");
const oddTotal = groups.odd?.[REDUCE]((sum, n) => sum + n, 0); // 4
// A possible group key may be absent, including for empty input.
```

## Contract and limitations

- Own enumerable string keys are data. Inherited, non-enumerable, and Symbol-keyed input properties are not copied. `__proto__`, `constructor`, and `toString` are supported as ordinary data keys; the shared prototype has a null root.
- Construction and query operations make shallow copies. Values remain shared references. Queries are mutable records, but operations do not mutate their source.
- `LIMIT` retains native `slice` semantics: negative numbers drop trailing entries, fractions truncate, `NaN` gives an empty result, and `Infinity` keeps all entries.
- Methods need their receiver: call `query[WHERE](predicate)`, not a detached method. Object spread and JSON on records retain data but lose query methods.
- Methods are shared and frozen, not bound per instance. This is a structural allocation choice, not a promise of a particular heap reduction or runtime speed.

## Numeric and grouped aggregation

These terminal methods work on records, eager ordered sequences, and lazy sequences. Each call consumes pending work immediately in source order, using original record keys in callbacks. There is no hidden source cache: repeated lazy calls rerun callbacks and observe changes to the query record.

| Terminal | Result |
| --- | --- |
| `[SUM]((value, key) => number)` | Sum, starting at `+0`; empty input returns `0` |
| `[AVERAGE]((value, key) => number)` | Sum divided by count; empty input returns `undefined` |
| `[MIN]((value, key) => number)` | Minimum; empty input returns `undefined` |
| `[MAX]((value, key) => number)` | Maximum; empty input returns `undefined` |
| `[STATS]((value, key) => number)` | `NumericStats`: `{ count, sum, average, min, max }` |
| `[COUNT_BY]((value, key) => K)` | `Partial<Record<K, number>>` with counts per string group |
| `[REDUCE_BY](keyFn, initial, reducer)` | `Partial<Record<K, A>>` with one accumulator per string group |

```ts
import {
  createQueryable, SUM, AVERAGE, MIN, MAX, STATS, COUNT_BY, REDUCE_BY,
} from "@ilokesto/queryable";

const sales = createQueryable({
  alice: { team: "red", amount: 10 },
  bob: { team: "blue", amount: 20 },
  carol: { team: "red", amount: 30 },
});
sales[SUM](sale => sale.amount); // 60
sales[AVERAGE](sale => sale.amount); // 20
sales[MIN](sale => sale.amount); // 10
sales[MAX](sale => sale.amount); // 30
sales[STATS](sale => sale.amount);
// { count: 3, sum: 60, average: 20, min: 10, max: 30 }
sales[COUNT_BY](sale => sale.team); // { red: 2, blue: 1 }

const totals = sales[REDUCE_BY](
  sale => sale.team === "red" ? "red" : "blue",
  _groupKey => ({ total: 0, members: [] as string[] }),
  (acc, sale, key) => {
    acc.total += sale.amount;
    acc.members.push(key);
    return acc;
  },
);
// Partial<Record<"red" | "blue", { total: number; members: string[] }>>
totals.red?.total; // 40
```

Numeric selectors are required and return `number` only. Use custom `REDUCE` for `bigint` totals, for example `query[REDUCE]((total, value) => total + value, 0n)` on a bigint query. `STATS` makes one pass and calls the selector exactly once per entry, computing all five fields without separately consuming the source. Each individual numeric terminal also calls its selector once per entry. Empty `STATS` returns `{ count: 0, sum: 0, average: undefined, min: undefined, max: undefined }`.

Numbers use JavaScript arithmetic without filtering or coercion: sum is left-to-right `+` from `+0`, average is that sum divided by count, and extrema follow `Math.min`/`Math.max`. `NaN` propagates into numeric results but still counts as an entry. Infinities and overflow are retained; adding opposite infinities produces `NaN`. Floating-point rounding follows source order. A sum of only `-0` is `+0` (and its average is `+0`); extrema retain a lone `-0`, while mixed zero signs produce `-0` for min and `+0` for max. Even after encountering `NaN`, all remaining entries and selectors are visited unless a callback throws.

`REDUCE_BY` accepts `keyFn(value, key)`, an **initial accumulator factory** `initial(groupKey)`, and `reducer(accumulator, value, key)`, in that argument order so the factory infers the reducer's accumulator type. For each entry it calls the key function, creates the accumulator if this is the first entry in that group, then invokes the reducer, including on the first entry. The factory runs exactly once per encountered group per terminal call, never for absent groups or empty input. Return a fresh object from the factory when groups need separate mutable state. The reducer's returned value replaces that group's accumulator, including `undefined`, `null`, `false`, `0`, and `""`; a stored `undefined` never reinitializes a group.

Both grouped terminals fold directly without retaining full groups. Their result has a null prototype, so `""`, `__proto__`, `constructor`, and `toString` are safe string group keys. Literal key unions remain inferred, but each property is optional because the group may be absent; use `Object.hasOwn(result, key)` to distinguish an absent group from a present `undefined` accumulator. Output property enumeration follows native object ordering, including integer-like keys. Within each group reducers see the stable source order. Errors from upstream work, selectors, factories, and reducers propagate immediately; later lazy consumption starts a fresh traversal and creates fresh accumulators.

`GROUP_BY` remains different: it eagerly materializes full snapshot groups that can be queried further. Use it when group contents are needed; use `COUNT_BY` or `REDUCE_BY` when only a per-group count or fold is needed.

## Lookup and default reads

These shared terminal methods work on records, ordered sequences, and lazy views in query order.

| Operation | Result |
| --- | --- |
| `[LAST]()` | Last value, or `undefined` when empty |
| `[AT](index)` | Value at a zero-based index; negative indexes count from the end |
| `[SINGLE](predicate?)` | Only matching value, or `undefined` for no match; throws `RangeError` on the second match |
| `[EVERY](predicate)` | Whether every value matches; `true` when empty |
| `[IS_EMPTY]()` | Whether no entry exists |
| `[INCLUDES](value)` | Whether a value exists using SameValueZero (`NaN` matches `NaN`, `0` matches `-0`, objects use identity) |
| `[FIND_ENTRY](predicate)` | First matching fresh `[key, value]` tuple, or `undefined` |
| `[FIRST_OR](value)` | First value, using the supplied fallback only when empty |
| `[FIRST_OR_ELSE](factory)` | First value, calling the zero-argument factory exactly once only when empty |

Predicates receive `(value, key)`. `SINGLE` without a predicate counts every entry; with a predicate it counts only matches. A stored `undefined` is still a match and a second such entry still throws. `SINGLE` and `FIND_ENTRY` preserve type guard narrowing. Returned tuples are fresh but their values remain shared references.

`AT` uses `Array.at` numeric coercion: fractions truncate toward zero, `NaN` selects index zero, and signed zero selects the first entry. Both infinities return `undefined` without iterating or executing pending lazy callbacks. Coercion errors propagate before iteration. A finite nonnegative index stops at the selected entry (or exhausts the query when out of range). A finite negative index consumes the whole query and buffers at most `min(entry count, abs(truncated index))` values. `LAST` also consumes the whole query. `SINGLE` consumes until exhaustion or its second match; the other reads stop as soon as their result is known. Repeated calls on lazy views repeat pending work.

Presence never depends on truthiness or on whether a value is `undefined`. Existing `FIRST` and `FIND` still return `undefined` for either absence or a stored `undefined`; default reads instead inspect entry presence and keep stored `0`, `false`, and `undefined` unchanged. Predicate and factory errors propagate unchanged.

```ts
import {
  createQueryable, AT, FIND_ENTRY, FIRST_OR, FIRST_OR_ELSE, SINGLE,
} from "@ilokesto/queryable";

const query = createQueryable<number | string | undefined>({ a: undefined, b: 0, c: "three" });
query[FIRST_OR](99); // undefined: entry "a" exists
query[FIRST_OR_ELSE](() => 99); // undefined: factory is not called
query[AT](-1); // "three"
query[SINGLE]((value): value is string => typeof value === "string"); // string | undefined
query[FIND_ENTRY]((value): value is string => typeof value === "string"); // [string, string] | undefined
```

## Bounds and prefixes

These shared Symbol operations retain original keys and query mode: records return records, and ordered or lazy sequences return sequences. They execute immediately on eager queries and defer work on lazy queries.

| Operation | Result |
| --- | --- |
| `[SKIP](n)` | Exclude the first `n` entries |
| `[TAKE_WHILE]((value, key) => boolean)` | Keep the matching prefix, excluding the first mismatch |
| `[DROP_WHILE]((value, key) => boolean)` | Exclude the matching prefix, including the first mismatch in the result |
| `[TAKE_LAST](n)` | Keep the last `n` entries in input order |
| `[DROP_LAST](n)` | Exclude the last `n` entries in input order |

All three numeric bounds use the same size normalization: truncate fractions toward zero, clamp negative sizes (including `-Infinity`) to zero, treat `NaN` as zero, and retain `Infinity`. Thus `SKIP(0)` and `DROP_LAST(0)` keep everything, while `TAKE_LAST(0)` is empty and does not read upstream. This does not change the signed `slice(0, n)` contract of `LIMIT`.

```ts
import {
  createQueryable, LAZY, SKIP, LIMIT, TAKE_WHILE, DROP_WHILE,
  TAKE_LAST, DROP_LAST, VALUES,
} from "@ilokesto/queryable";

const query = createQueryable({ a: 1, b: 2, c: 3, d: 2 });
query[LAZY]()[SKIP](1)[LIMIT](2)[VALUES](); // [2, 3]
query[TAKE_WHILE](n => n < 3)[VALUES](); // [1, 2]
query[DROP_WHILE](n => n < 3)[VALUES](); // [3, 2]
query[TAKE_LAST](2)[VALUES](); // [3, 2]
query[DROP_LAST](2)[VALUES](); // [1, 2]
```

Use `SKIP(start)[LIMIT](length)` for a nonnegative window; there is no separate `SLICE` operation. Integer record keys still follow native object ordering; sequence keys retain their upstream order. Stored `undefined` and special keys are retained normally.

`TAKE_WHILE` stops at the first mismatch and supports type guards. `DROP_WHILE` stops calling its predicate after the first mismatch; its remaining values are not narrowed. Both predicates receive the original key.

On lazy queries, `SKIP(n)[FIRST]()` pulls at most `n + 1` entries and `TAKE_WHILE(predicate)[LIMIT](k)` stops after the required prefix without testing a later entry. `TAKE_LAST(n)` must finish upstream before yielding anything and stores at most `n` entries in a ring buffer for finite sizes. `DROP_LAST(n)` uses at most `n` buffered entries and needs `n + 1` upstream entries for its first output; early terminals can then stop it. Neither operation moves ahead of sorting, sequence `PICK`, or negative `LIMIT` barriers.

`SKIP(Infinity)` and `DROP_LAST(Infinity)` consume upstream and return no entries; the latter stores none. `TAKE_LAST(Infinity)` consumes and buffers the entire input before returning all entries. Each consumption gets fresh counters, predicate state, and buffers, including after early termination or an error. Lazy callbacks and errors remain deferred, and mutations between consumptions remain visible.

## Iterable sources and key identity

`createQuerySequence(factory, options?)` creates a lazy sequence from a factory of
`Iterable<readonly [string, T]>`. Construction does not call the factory. Each
consumption calls it again: return a fresh iterator or a repeatable iterable, not
the same exhausted generator. There is no result cache or automatic rewind.

```ts
import { createQuerySequence, iterateEntries, iterateValues } from "@ilokesto/queryable";

const rows = new Map([["2", 20], ["1", 10]]);
const query = createQuerySequence(() => rows.entries());
const entries = iterateEntries(query); // no consumption yet
[...entries]; // [["2", 20], ["1", 10]]
rows.set("2", 30);
[...iterateValues(query)]; // [30, 10]
```

`iterateEntries(query)` and `iterateValues(query)` accept records and sequences
without first collecting an array. Each iterator is independent. Entry views
return fresh mutable tuples; changing them does not change a buffered query.
Values remain shallow references. A query itself has no ambiguous default
iterator: choose entries or values explicitly.

External entries must be two-element arrays with string keys. Values, including
`undefined`, Symbols, and opaque objects, are not inspected. Malformed entries
throw `TypeError` when pulled. Acquired generators close on early exit or a
downstream error; `LIMIT(0)` does not acquire the source.

The `duplicateKeys` option makes key collisions explicit:

| Policy | Behavior |
| --- | --- |
| `"error"` (default) | Throw `DuplicateKeyError`, whose `key` identifies the repeated key, when that entry is pulled |
| `"first"` | Keep the first value, including a stored `undefined`; later occurrences are skipped |
| `"last"` | Consume the whole source before yielding; use the last value while keeping each key's first position |

Every consumption creates fresh identity state. The streaming policies retain a
set of observed keys; `"last"` buffers a map of all distinct keys. Prefix
consumers validate only what they pull, not the unconsumed tail. Full consumers
therefore reject duplicate keys by default instead of silently overwriting them.
`PICK`, grouping, sorting, and collection outputs receive the same unique-key
entries. This is also the identity boundary for future multi-source operations.
`TO_OBJECT` still intentionally restores native object ordering for integer keys.

## Indexed joins

`GROUP_JOIN(inner, outerKey, innerKey, project)` preserves each outer key and
returns exactly one value per outer entry. `project(value, matches, outerKey)`
receives a fresh array of readonly `[innerKey, innerValue]` tuples, empty for no
match. It returns a record for a record receiver and a sequence for a sequence.

`INNER_JOIN` and `LEFT_JOIN` use the same first three arguments, followed by
`project(value, match, outerKey)` and optional `{ duplicateKeys }`. Their
projection **must return `[generatedKey, result]`**, with a string key chosen by
the caller. Both return ordered sequences. Inner matches are
`{ matched: true, key: string, value: I }`. LEFT_JOIN also passes
`{ matched: false }` once for an unmatched outer entry: matched `undefined` is
not absence. INNER_JOIN emits nothing for an unmatched outer entry. Empty outer
input produces no outputs and never invokes outer selectors or projections.
Selectors receive `(value, originalKey)` from their own source; downstream
callbacks receive the explicit generated keys.

```ts
import {
  createQueryable, GROUP_JOIN, INNER_JOIN, LEFT_JOIN, LAZY, VALUES,
} from "@ilokesto/queryable";

const users = createQueryable({ alice: 1, bob: 2 });
const orders = createQueryable({ first: { user: 1, total: 10 }, second: { user: 1, total: 20 } });
users[GROUP_JOIN](orders, id => id, order => order.user,
  (_id, matches) => matches.length)[VALUES](); // [2, 0]
users[LAZY]()[INNER_JOIN](orders, id => id, order => order.user,
  (_id, match, key) => [`${key}/${match.key}`, match.value.total])[VALUES](); // [10, 20]
users[LEFT_JOIN](orders, id => id, order => order.user,
  (_id, match, key) => [match.matched ? `${key}/${match.key}` : key,
    match.matched ? match.value.total : undefined])[VALUES](); // [10, 20, undefined]
```

Join keys use native Map SameValueZero: `NaN` matches itself, signed zeros match,
and objects and Symbols use identity without string coercion. Outer order
(including SORT order) is preserved, followed by inner source order for each
match. Generated keys cross the same identity boundary as `createQuerySequence`:
`"error"` is the default, `"first"` keeps the first value, and `"last"` buffers
all generated entries, retaining each key's first position and last value.
Special string keys are ordinary data. Prefix consumers check only pulled
generated keys with streaming policies; no implicit numbering or overwrite occurs.

Each consumption builds a **fresh inner Map of match arrays**, retaining all
inner entries: O(inner count) memory plus distinct join-key buckets. The inner
source is fully consumed and its selector called once per entry before acquiring
the outer iterator, even when outer input is empty. Each pulled outer entry calls
its selector once; GROUP_JOIN projects once per outer entry, INNER_JOIN once per
pair, and LEFT_JOIN once per pair or unmatched outer entry. GROUP_JOIN copies its
match tuples for each projection. Expanded output can reach outer count times
inner count for many-to-many joins; eager results retain all output entries.
Identity checking additionally retains generated keys, or full results for `"last"`.
Infinite inner sources cannot yield join output.

Record and eager sorted receivers execute immediately; lazy receivers defer
indexing and callbacks until demand. `LIMIT(0)` downstream of a lazy join acquires
neither source. After indexing, streaming policies allow early outer termination
and close acquired iterators. Callback and source errors propagate unchanged and
close active iterators. Repeat or interleaved lazy consumers have independent
indexes and observe live source changes; eager results are snapshots. GROUP_JOIN
is not GROUP_BY: it follows receiver mode, while existing GROUP_BY remains eager.
